## Accepted architecture decisions

All decisions in this section are **Accepted** for the current Entity MVC and Unity presentation
binding phase. Later changes require an explicit superseding ADR rather than silently weakening
these boundaries.

### ADR-001 — Model state belongs to GameSession/World registries

Authoritative gameplay state is stored as pure C# struct state owned by `GameSession` and its
registries. A GameObject observes that state through a stable identity and a read-only snapshot;
it is never the model owner. The current player implementation uses session-scoped GUID
`PlayerId` as the entity identity and `PlayerModel` as the struct snapshot.

This keeps scene unload, prefab replacement, Unity object destruction, and presentation pooling
from deciding model lifetime or persistence. A snapshot copy can diverge locally without mutating
the registry; mutations must go through a domain System or command processor.

### ADR-002 — Domain rule coordinators are named Systems

Pure simulation rules use names such as `HealthSystem` and `CommandProcessor`. Unity components
named Controller are input, interaction, command-sending, or external-event bridges. A GameObject
Controller does not implement health, damage, inventory, or other authoritative rules.

This naming boundary prevents the two meanings of “Controller” from collapsing into one component
that owns input, domain rules, and presentation state simultaneously.

### ADR-003 — Binder projection is one-way

The default presentation flow is read-only state reader → Binder → View. Input takes the separate
Controller → command sender path. `EntityViewBinder` may cache only the last immutable render
revision/state needed to suppress duplicate projection; it does not retain an authoritative model
copy or write back through the reader.

Unity Physics state is a separate boundary. A Binder never assigns the predicted Rigidbody
Transform as part of model projection.

### ADR-004 — FishNet adapters remain outside MVC contracts

FishNet `NetworkBehaviour`, broadcasts, prediction DTOs, synchronization, and connection identity
remain in the networking adapter layer. Binder and View contracts consume domain/player
presentation values and do not reference FishNet types.

`BlockPlayerController` is the deliberate migration exception: it remains the existing
PredictionRigidbody network adapter while input and visual responsibilities move to co-located
components. Preserving working prediction behavior takes priority over renaming or replacing the
adapter in one step.

### ADR-005 — Server authority and client presentation use sibling scopes

`ApplicationLifetimeScope` owns two separate branches: server/Host authority in
`ServerSessionLifetimeScope`, and local client presentation in
`ClientPresentationLifetimeScope`. `SceneLifetimeScope` is a child of the client branch. In a
Host process, the server and client branches remain siblings; a View cannot resolve the server
`GameSession` or `PlayerRegistry` through its parent.

This follows VContainer's single-parent visibility model and prevents a Host-only shared singleton
from disguising synchronization bugs that would appear on a remote client.

### ADR-006 — EntityLifetimeScope is opt-in

Ordinary entities, blocks, and chunks do not receive a per-GameObject LifetimeScope. A complex
Player or vehicle may introduce an entity scope only when it owns multiple independent per-entity
services or disposable resources and defines an explicit pool/recreation policy.

The current Player prefab uses no entity scope. Application adapters and the readiness gate provide
the required context without per-entity DI-container, GC, or pool-lifetime overhead.

### ADR-007 — Unity Physics owns dynamic Rigidbody state

Unity Physics owns dynamic Rigidbody position, rotation, and velocity. FishNet Prediction remains
the network prediction/reconciliation path. Domain rules may read value snapshots through
`IPhysicsQuery` or issue explicit commands through `IPhysicsCommands`; they do not become a second
per-tick transform writer.

Pure domain tests therefore require no Unity physics types, while actual collision and Rigidbody
execution—including a headless server—still requires the Unity runtime. `PhysicsMode.TimeManager`
is the sole physics-step owner.

### ADR-008 — WorldHost EditMode authoring remains supported

EditMode `WorldHost`, Block Paint, serialized block records, mesh preview, and RegionJSON workflows
remain intact and usable without scene DI. At runtime, the authoritative WorldCore belongs to the
server session and `WorldHost` is a borrowed client-view/renderer bridge.

This phase does not change scene YAML or RegionJSON formats and does not rewrite the chunk mesh
pipeline.

### ADR-009 — Existing player prediction is retained

The current `[Replicate]`, `[Reconcile]`, `PredictionRigidbody`, and FishNet TimeManager tick path
remain in place. A competing `NetworkTransform` is not added to the Player and project code does
not manually advance the same PhysicsScene.

MVC separation is intentionally incremental so a presentation refactor cannot silently replace
the already working movement protocol.

### ADR-010 — Persistence remains the preceding phase's responsibility

This phase reuses the existing session archive, storage, and restore transaction. It does not
invent a second snapshot format or reimplement save/load. Its responsibility is the boundary after
restore: replacement client state and newly created Unity objects must bind without retaining the
old reader, identity, subscription, or View cache.

## Scope exclusions

The following are explicit non-goals for this phase:

- ECS/DOTS migration or replacement of Unity Physics with a pure C# physics engine.
- A LifetimeScope on every entity, block, chunk, or pooled visual.
- Replacing FishNet with Mirror or Netcode for GameObjects.
- Replacing PredictionRigidbody movement with NetworkTransform movement.
- A second replicated WorldCore, a new chunk-storage format, or per-block GameObjects/Binders.
- Multi-room hosting, scene stacking, full rollback/replay, interest management, or bandwidth
  optimization.
- Rewriting the existing renderer, ProPixelizer integration, commercial assets, or texture packs.
- Replacing the existing uGUI flow with UI Toolkit.
- Moving prefab-specific scripts out of their `Assets/Entities/<Prefab>/` co-location or otherwise
  bypassing `AGENTS.md`.

## Resolved implementation choices

1. The Phase 1 `PlayerModel`, `PlayerRegistry`, and `GameSession` already exist and are reused.
2. The client replica is the independent `ClientStateCoordinator` store. Host presentation reads
   the same client interface as a remote client and never shortcuts to server state.
3. A replicated GUID becomes `PlayerId` through `BlockPlayerController`'s FishNet callback. The
   `PlayerPresentationBindingGate` waits independently for identity and replica dependencies.
4. `SimulationWorld` owns the authoritative runtime WorldCore. Runtime `WorldHost` borrows the
   client replica; EditMode `WorldHost` retains authoring ownership.
5. The Player prefab has no EntityLifetimeScope because it currently owns no independent
   per-entity service graph requiring one.

## Assembly and dependency direction

`MF2.Game.Domain` references only `MF2.World.Runtime`, Collections, and Mathematics. It has no
FishNet, VContainer, uGUI, Editor, Rigidbody, Collider, Transform, or PhysicsScene dependency.
`noEngineReferences` remains disabled because Unity 6 resolves Collections/Mathematics types
through Unity engine facade assemblies, but the source-level boundary is covered by reflection
tests.

Unity/FishNet/VContainer adapters remain in `MF2.Game`. FishNet connection IDs never enter the
domain; `GameCommandNetworkAdapter` owns the connection-to-GUID `PlayerId` map.

## Scope topology and disposal

The persistent `NetworkBootstrap` owns `ApplicationLifetimeScope`.

- `ServerSessionLifetimeScope` is created explicitly only when this process starts a server.
- `ClientPresentationLifetimeScope` is a separate application child and owns the client replica.
- `SceneLifetimeScope` is presentation-only and is parented under the client-presentation scope.
  It cannot resolve `GameSession`.
- Dedicated processes do not create client or scene-presentation scopes.

VContainer 1.19 tracks scoped `IDisposable` objects and disposes them in reverse creation order.
The session scope is the single disposal owner: `GameSession.Dispose` clears managed session state,
then `SimulationWorld.Dispose` releases `WorldCore`. The coordinator calls `Stop` for the gameplay
state transition and disposes the scope once; it never manually disposes the world.

`DisconnectAndReturnToOutgame` explicitly ends the server session before stopping FishNet. FishNet
stopped callbacks and MonoBehaviour disable/destroy hooks are idempotent safety nets.

## World ownership

`SimulationWorld` is the sole PlayMode owner of the authoritative `WorldCore`. There is no second
mutable block dictionary.

`WorldHost` keeps its current EditMode authoring ownership, serialized block records, paint tool,
storage, and mesh rebuild behavior. In PlayMode it is a borrowed client-view bridge and never
disposes the server world or accepts authoring mutation. Destroying or disabling a runtime view
therefore cannot destroy the authoritative session world.

Each authoritative tick performs one command drain and one `WorldCore.Flush`. Native `Changes` and
`DirtyChunks` views are copied immediately into immutable managed `TickDelta` arrays before any
renderer, persistence, or network consumer sees them.

## Tick and physics order

FishNet 4.7.3 source was checked rather than assuming Unity callback order. With
`PhysicsMode.TimeManager`, the fixed package source executes this order:

1. `OnPreTick`, then inbound iteration.
2. `PredictionManager.ReconcileToStates`, then `OnTick` (including player replicate input).
3. pre-physics notification, `Physics.Simulate`/`Physics2D.Simulate`, post-physics notification.
4. `OnPostTick`, then `PredictionManager.SendStateUpdate`, then outbound iteration.

`ServerSessionRunner` subscribes once to `OnPostTick`, so the domain step sees completed server
physics and does not simulate physics itself. FishNet events use subscription order rather than a
public callback-priority API. The runner is normally subscribed before dynamically spawned player
callbacks, so this implementation deliberately does not require player `CreateReconcile` to have
run before the domain step. If a future rule requires post-reconcile data rather than merely
post-physics data, it must add an explicit phase bridge instead of relying on subscription order.

`BlockPlayerController` keeps FishNet PredictionRigidbody replicate/reconcile behavior. No
NetworkTransform was added. The session-scoped `UnityPhysicsAdapter` maps stable `PlayerId` values
to live Rigidbody instances and exposes only Mathematics value DTOs through domain ports. It never
calls `Physics.Simulate`; PhysX contact-cache determinism is intentionally not promised by session
restore.

## Command authority

The client payload contains no trusted player ID. FishNet supplies the authenticated sender, which
is mapped to a server-generated `PlayerId`. Domain submission checks session phase, registered
identity, empty/invalid commands, and the exact `WorldCore` fill limit before queueing.

For network player commands, `ServerWorldCommandAuthorizer` additionally requires:

- a currently registered server Rigidbody for the mapped player;
- a stable block ID present in `BlockRegistryManifest` (Air is valid only for removal);
- command bounds within the configured interaction reach.

The manifest is serialized on `ApplicationLifetimeScope` by the multiplayer slice builder. Direct
server/domain tooling may supply a different pure authorizer explicitly.

The world-command gateway is an authenticated FishNet `IBroadcast`, not a `ServerRpc`, because the
gateway is an application-lifetime component rather than a spawned `NetworkBehaviour`. FishNet
4.7.3 supplies the authenticated `NetworkConnection` to the server handler, so the trust boundary
is equivalent without introducing a synthetic persistent `NetworkObject`. Commands use the
reliable channel explicitly, carry a client-local monotonic sequence, reject replay/out-of-order
envelopes, and are rate-limited per authoritative session tick. The payload carries no player or
connection identity.

Tick observers are invoked independently. An exception in network replication or another
consumer is reported by the runner but cannot prevent another observer from receiving the already
captured managed delta, cannot re-run `WorldCore.Flush`, and cannot abort later FishNet post-tick
callbacks.

## Dynamic prefab injection and pooling

The current `BlockPlayer` prefab has no VContainer injection requirement. Its `Awake` initializes
only co-located Rigidbody, prediction, input and view components; application/session services are
bound by the persistent adapters after FishNet spawn callbacks. Consequently no custom object pool
or forced `InjectGameObject` call is installed merely for architectural symmetry.

On the server, `PlayerSpawner` configures domain identity and physics/network maps before FishNet
`Spawn`. Remote clients are created by FishNet 4.7.3's configured object pool and are bound by
`PlayerReplicationAdapter.OnSpawnedAdd`. Reuse cleanup goes through FishNet stop/reset callbacks
and `PlayerPresentationBindingGate.ResetForReuse`; it is separate from session-scope disposal. If a
future network prefab gains `[Inject]` members required before `OnStartNetwork`, both server and
client retrieval paths must be replaced by a custom FishNet pool/factory that calls
`InjectGameObject` before spawn callbacks. Calling it only in `PlayerSpawner` would be invalid for
remote clients, and calling it after ordinary `Instantiate` would still be too late for `Awake`.

## Replication and late join

World and player replication use separate managed snapshot/delta DTOs. A client delta cannot create
or replace a replica: a matching initial snapshot is the ordering barrier. Session IDs, a
process-monotonic persisted session generation, and monotonic ticks reject stale or cross-restore
deltas. A restore always advances beyond both the archive generation and the active process
watermark, so an in-flight packet from the pre-restore session cannot mutate the replacement.
Disconnect clears the client replica.

Authentication sends current world and player snapshots. A successful restored-session swap also
broadcasts fresh snapshots to already-connected clients. The current initial world snapshot is a
complete sparse block list; chunk streaming/compression is a later scalability step, not hidden in
this implementation.

## Player GameObject MVC and readiness

The previous `BlockPlayerController` combined input, predicted physics, camera, and rig visuals.
The migration keeps the FishNet prediction methods in place while moving presentation work behind
small prefab-local components:

| Responsibility | Runtime type | State authority |
|---|---|---|
| health/life rules | `PlayerModel`, `PlayerRegistry`, `HealthSystem` | server session |
| owner input capture | `BlockPlayerInputSource` | local frame cache only |
| prediction/reconcile | `BlockPlayerController` | FishNet + Unity Rigidbody |
| camera/rig/visuals | `BlockPlayerView` | presentation output only |
| replica projection | `EntityViewBinder` | read-only client snapshot |
| spawn/DI ordering | `PlayerPresentationBindingGate` | no gameplay state |

The binder subscribes before its initial read, renders immediately, compares only immutable last
render state, and treats repeated bind/unbind as safe. The readiness gate accepts dependency-ready
and network-ID-ready in either order. Client despawn, presentation-scope teardown, and pool reuse
clear both inputs, so a reused object cannot retain the previous player's identity or subscription.

## Minimal world presentation slice

`WorldCommandDebugInput` is the non-player reuse proof for the command/binding architecture. It
sends a nearby block toggle through `IGameCommandSender`; the server validates and applies it once,
then replication updates the client-owned `WorldCore`. `WorldViewBridge` projects only world
replacement/dirty-flush events into the existing chunk renderer. It creates no per-block scope,
GameObject, or binder and does not bypass the EditMode paint/storage path.

## Persistence transaction

`SessionArchiveSnapshot` stores session ID, generation, phase, tick, elapsed time, seed, immutable
player snapshots, and a managed sparse world snapshot. It contains no GameObject, FishNet object,
connection, or native container. Capture is rejected while commands or player mutations remain
outside a completed authoritative tick boundary; a manual save therefore observes one completed
logical tick rather than silently dropping queued work.

`SessionJsonStorage` writes a new immutable generation:

1. Write all chunks with the existing `RegionJsonWorldStorage` into a staging generation.
2. Hash the sorted RegionJSON files, write that checksum plus schema/session metadata to the
   session manifest, and flush it.
3. Hash the exact manifest bytes and rename the staging directory to its committed generation name.
4. Atomically replace `current.json` with the generation and manifest checksum, preserving the
   previous pointer as `current.json.bak`.

The pointer is the commit marker. A failure before step 4 leaves the previous generation live.
Load verifies the pointer/schema, manifest checksum, RegionJSON checksum, structural RegionJSON
validation, and chunk count before constructing a candidate. Backups are loaded only through the
explicit backup API and are never silently promoted.

`ServerSessionCoordinator.RestoreServerSession` creates and validates a complete candidate scope,
world, players, and clock before stopping the current scope. Corrupt or unsupported storage data
therefore cannot partially mutate the live session. After candidate commit, the old scope receives
one Stop transition and one scope disposal; replication adapters then publish fresh snapshots with
the advanced generation.

## Current explicit limits

- Save/restore services and transactional storage are implemented, but no player-facing save-slot
  UI or autosave policy is defined yet.
- Initial snapshots are complete sparse snapshots rather than streamed chunk windows.
- Physics persistence DTOs exist at the port boundary, but Rigidbody restore is not included in the
  current block/player-health archive because no persistent physics entities are yet defined.
- Player NetworkObject IDs, current connections, Rigidbody position/rotation/velocity, and PhysX
  contact caches are not persisted. A restored player identity/health record is domain state, not a
  claim that its current predicted Player GameObject or motion state was reconstructed. Connected
  player continuity needs an account/slot-to-PlayerId rebind policy before live-session restore is
  exposed as a player-facing feature.
- The current player model persists identity and health; inventory/rules can be added to the same
  immutable archive contract when those domain features exist.
